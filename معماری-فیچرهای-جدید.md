# معماری فیچرهای جدید — درآمدزایی و رشد (Lovely)

**نسخه:** ۱.۰ — سند طراحی (Design Spec)
**تاریخ:** ۱۴۰۵/۰۶/۰۸
**دامنه:** معماری فول‌استک برای ۲۲ فیچر جدید با تمرکز روی درآمدزایی و رشد
**وضعیت:** فقط طراحی — هیچ کدی اجرا یا تغییر داده نشده است. این سند برای پیاده‌سازی توسط خودت آماده شده.

> **چطور از این سند استفاده کنی:** اول بخش «بنیان مشترک» را کامل بساز (بدون آن هیچ فیچری کار نمی‌کند)، بعد فیچرها را فاز به فاز طبق بخش «ترتیب پیاده‌سازی» جلو ببر. هر فیچر یک بلوک مستقل دارد شامل: هدف، تغییرات Prisma، اندپوینت‌ها (با شکل کامل درخواست/پاسخ)، فرانت‌اند، و حالات لبه.

## فهرست فیچرها

**اقتصاد پایه (Foundation-level):**
۱. کیف پول سکه و دفترکل تراکنش · ۲. بسته‌های سکه با پاداش پلکانی · ۳. پرداخت با Telegram Stars

**تقویت دیده‌شدن (Revenue):**
۴. بوست پروفایل · ۵. اسپاتلایت (نورافکن) · ۶. پک سوپرلایک · ۷. بازگردانی سواایپ (Rewind)

**بینش‌های ویژه (Revenue):**
۸. بازدیدکنندگان پروفایل · ۹. رسید خواندن پیام · ۱۰. آشکارسازی لایک‌کننده‌ها · ۱۱. حالت ناشناس پولی

**اشتراک و پیشنهاد (Revenue):**
۱۲. اشتراک چندلایه + مدیریت · ۱۳. فروش ویژهٔ زمان‌دار · ۱۴. کد تخفیف و کوپن

**اقتصاد هدیه (Revenue + Social):**
۱۵. فروشگاه هدیهٔ پیشرفته · ۱۶. ارسال سکه / تیپ

**حلقه‌های رشد (Growth):**
۱۷. برنامهٔ دعوت دوستان · ۱۸. ورود روزانه و استریک · ۱۹. مأموریت‌ها و کوئست‌ها · ۲۰. چرخ شانس روزانه · ۲۱. پاداش جدول برترین‌ها · ۲۲. برنامهٔ آمباسادور

## اصول طراحی (Cross-cutting)

پیش از فیچرها، چند تصمیم معماری که در سرتاسر سند فرض شده‌اند:

**۱. دفترکل سکه، منبع حقیقت واحد است.** هر سکه‌ای که وارد یا خارج می‌شود یک ردیف در `CoinTransaction` می‌سازد. مقدار `User.coinBalance` صرفاً یک کَش است که *در همان تراکنش* به‌روزرسانی می‌شود. هیچ اندپوینتی مستقیماً `coinBalance` را دستکاری نمی‌کند؛ همه از طریق هلپر `spendCoins`/`creditCoins` (در `lib/coins.js`) عبور می‌کنند تا موجودی و دفترکل هرگز واگرا نشوند.

**۲. همه‌چیز ایدمپوتنت است.** هر عملیات پولی یا پاداشی یک `idempotencyKey` یکتا دارد (مثلاً `checkin:{userId}:{date}` یا `payment:{telegramChargeId}`). تلاش دوباره با همان کلید، تراکنش تکراری نمی‌سازد. این جلوی دبل‌اسپند، ریتری‌های وب‌هوک، و دابل‌تپ کاربر را می‌گیرد.

**۳. احراز هویت همان الگوی موجود است.** تمام اندپوینت‌های نوشتنی با میان‌افزار `authorizeTelegramId` (از `lib/telegramAuth.js` که قبلاً ساخته شد) محافظت می‌شوند تا کاربر فقط بتواند روی حساب خودش عمل کند. **استثنا:** وب‌هوک پرداخت تلگرام سرور-به-سرور است و با شناسهٔ کاربر محافظت نمی‌شود؛ در `bot.js` از طریق رویدادهای `pre_checkout_query` و `successful_payment` و صحت‌سنجی payload اعتبارسنجی می‌شود.

**۴. زمان ریست روزانه ثابت است.** همهٔ ریست‌های روزانه (چک‌این، چرخ شانس، سقف لایک) بر مبنای نیمه‌شب به وقت `Asia/Tehran` حساب می‌شوند. برای مقایسه از «کلید روز» به‌شکل `YYYY-MM-DD` در همان تایم‌زون استفاده کن تا از باگ‌های مرزی UTC جلوگیری شود.

**۵. تراکنش‌های اتمیک برای هر عملیات چندمرحله‌ای.** خرج‌کردن سکه + ثبت اثر آن (مثلاً فعال‌کردن بوست) همیشه داخل یک `prisma.$transaction` انجام می‌شود؛ اگر هر مرحله شکست بخورد، سکه هم کسر نمی‌شود.

**۶. اعلان‌ها متمرکزند.** هر پاداش/رویداد پولی از هلپر موجود `notify()` استفاده می‌کند و انواع جدید اعلان اضافه می‌شوند (پایین‌تر).

**۷. ریت‌لیمیت روی اندپوینت‌های حساس.** اندپوینت‌های خرج‌کردن، اسپین، چک‌این و ردیم‌کردن کوپن باید محدودیت نرخ داشته باشند (مثلاً حداکثر N درخواست در دقیقه به‌ازای هر کاربر) تا سوءاستفاده مهار شود.

## بنیان مشترک (این را اول بساز)

### الف) فیلدهای جدید مدل `User`

این فیلدها به مدل `User` در `prisma/schema.prisma` اضافه می‌شوند:

```prisma
model User {
  // ... فیلدهای موجود ...

  // — اقتصاد سکه —
  coinBalance          Int       @default(0)   // کَش موجودی؛ برابرِ جمع CoinTransaction
  totalCoinsPurchased  Int       @default(0)   // مجموع سکهٔ خریداری‌شده در طول عمر (تحلیل)

  // — تقویت دیده‌شدن —
  boostActiveUntil     DateTime?               // انقضای بوست فعال
  spotlightUntil       DateTime?               // انقضای حضور در اسپاتلایت
  superLikeBalance     Int       @default(0)   // سوپرلایک خریداری‌شده (جدا از سقف رایگان روزانه)
  rewindAvailable      Int       @default(0)   // تعداد ری‌وایندِ در دسترس (پولی)

  // — اشتراک —
  subscriptionTier     String?                 // null | "gold" | "platinum" | "diamond"
  subscriptionUntil    DateTime?               // تاریخ پایان اشتراک پرداخت‌شده
  autoRenew            Boolean   @default(true)

  // — رشد / دعوت —
  referralCode         String?   @unique       // کد دعوت مختص همین کاربر
  referredById         Int?                    // چه کسی او را دعوت کرده (User.id)
  referredBy           User?     @relation("UserReferrals", fields: [referredById], references: [id])
  referrals            User[]    @relation("UserReferrals")

  // — استریک / پاداش روزانه —
  streakCount          Int       @default(0)   // تعداد چک‌این‌های متوالی
  streakFreezeUntil    DateTime?               // محافظت استریک‌فریز فعال
  lastCheckInAt        DateTime?
  lastWheelSpinAt      DateTime?

  // — روابط جدید (لیست معکوس) —
  coinTransactions     CoinTransaction[]
  payments             PaymentInvoice[]
  subscriptions        Subscription[]
  promoRedemptions     PromoRedemption[]
  boosts               Boost[]
  profileVisitsMade    ProfileVisit[] @relation("Visitor")
  profileVisitsGot     ProfileVisit[] @relation("Visited")
  featureUnlocks       FeatureUnlock[]
  checkins             DailyCheckin[]
  missionProgress      MissionProgress[]
  wheelSpins           WheelSpin[]
  giftsSent            Gift[]     @relation("GiftSender")   // اگر از قبل نیست
  giftsReceived        Gift[]     @relation("GiftReceiver") // اگر از قبل نیست
  ambassador           Ambassador?
}
```

> **نکتهٔ مهاجرت:** چون `referredBy`/`referrals` یک self-relation است، نام رابطه (`"UserReferrals"`) الزامی است. `referralCode` یکتاست و باید هنگام ساخت کاربر مقداردهی شود (تولید کد کوتاه، بخش فیچر ۱۷).

### ب) مدل‌های جدید Prisma

مدل هستهٔ اقتصاد — **دفترکل سکه**:

```prisma
model CoinTransaction {
  id             Int      @id @default(autoincrement())
  userId         Int
  user           User     @relation(fields: [userId], references: [id])
  amount         Int      // مثبت = واریز، منفی = برداشت
  balanceAfter   Int      // موجودی پس از این تراکنش (برای حسابرسی)
  type           String   // purchase | spend_boost | spend_superlike | spend_reveal | spend_rewind
                          // | gift_sent | gift_received | tip_sent | tip_received
                          // | referral_reward | checkin_reward | mission_reward
                          // | wheel_reward | leaderboard_reward | ambassador_payout | promo | refund | admin
  refType        String?  // نوع موجودیت مرتبط: "boost" | "gift" | "event" | ...
  refId          Int?     // شناسهٔ موجودیت مرتبط
  idempotencyKey String?  @unique   // جلوگیری از تراکنش تکراری
  meta           Json?    // جزئیات دلخواه (مثلاً برچسب محصول)
  createdAt      DateTime @default(now())

  @@index([userId, createdAt])
}
```

### ج) لایه‌های مشترک `lib/`

**`lib/coins.js`** — تنها راه جابه‌جایی سکه:

```
creditCoins(tx, userId, amount, { type, refType?, refId?, idempotencyKey?, meta? })
  → داخل تراکنش: قفل ردیف کاربر، افزودن amount به coinBalance،
    درج CoinTransaction با balanceAfter، برگرداندن موجودی جدید.
    اگر idempotencyKey تکراری بود، بی‌سروصدا همان نتیجهٔ قبلی را برگردان.

spendCoins(tx, userId, amount, { type, ... })
  → مثل بالا ولی منفی؛ اگر موجودی کافی نبود throw InsufficientCoins
    (که در روتر به پاسخ 402 «سکهٔ ناکافی» ترجمه می‌شود).

getBalance(userId) → عدد coinBalance (کش).
```

**`lib/entitlements.js`** — بررسی دسترسی‌های پولی:

```
isPremium(user) → آیا subscriptionUntil در آینده است.
tierPerks(user) → آبجکت مزایا از SubscriptionPlan.perks (یا مقادیر پیش‌فرض رایگان).
hasFeature(userId, feature) → آیا FeatureUnlock فعال دارد یا tier آن را شامل می‌شود.
isBoosted(user) → boostActiveUntil در آینده؟
dailyLikeLimit(user) → بر اساس tier (رایگان: عددی محدود، پرمیوم: بی‌نهایت).
```

**`lib/notify.js`** (موجود) — انواع جدید اعلان که باید به union فیلد `Notification.type` اضافه شوند:
`reward`, `payment`, `subscription`, `boost_ended`, `referral`, `promo`, `gift` (اگر نیست), `tip`.

### د) نقشهٔ ماژول‌های روتر جدید

هم‌راستا با ساختار فعلی (`routes/*.js` که زیر `/api` سوار می‌شوند)، پنج ماژول جدید اضافه کن. **همه باید پیش از catch-all در `server.js` سوار شوند** (خط ۶۶۶ فعلی):

```js
app.use("/api", require("./routes/economy"));       // فیچرهای ۱،۲،۳،۱۳،۱۴
app.use("/api", require("./routes/boosts"));        // فیچرهای ۴،۵،۶،۷
app.use("/api", require("./routes/insights"));      // فیچرهای ۸،۹،۱۰،۱۱
app.use("/api", require("./routes/subscriptions")); // فیچر ۱۲
app.use("/api", require("./routes/growth"));        // فیچرهای ۱۷–۲۲
// فیچرهای ۱۵،۱۶ (هدیه/تیپ) به routes/profile.js موجود افزوده می‌شوند
```
